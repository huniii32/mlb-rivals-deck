# 서버 이벤트 검증판

시뮬레이터의 이벤트 화면을 Supabase RPC와 연결한다. 서버 적용 전에는 준비 안내만 표시하며 브라우저 기록을 정식 참여 기록으로 대체하지 않는다. 기존 데모(`/demo/events.html`)와 개인용 수집 프로그램은 별개다.

## 운영 규칙

- **등록 덱 + 기존 비밀번호**로 즉시 참여한다. 참가자 이메일 로그인이나 운영자 사전 승인은 없다. 비밀번호 확인으로 발급한 덱 세션을 서버에서 검증하며, 이벤트마다 등록 덱 ID당 참가 기록 하나를 유지한다. 다른 기기에서 같은 덱을 비밀번호로 가져와도 기존 도전 횟수와 응모권을 이어간다.
- 최고급 변경권 / 시그니처 선발 투수 / S 레벨 / 잠금 없는 3슬롯. 총 5회 중 최고 합계 점수로 순위를 정한다.
- 동점이면 해당 최고점을 **서버에서 먼저 달성한 참가자** 우선. 서버 타임스탬프까지 같으면 서버 기록 순번을 사용한다.
- 덱 등록, 스킬 도전, 이벤트 전용 모먼트 조합 체험, 이벤트 전용 일반 HOF 체험에서 각각 응모권 1장. 참여 완료 후 받기 버튼을 눌러 발급하며 최대 4장이다.
- 조합 체험은 모먼트 1장 + 등급 보호권, 구단 제한 없음(슈프림 15%, 모먼트 85%). 후보 5장을 확인하고 뒤집힌 카드 1장을 고른 뒤 참여로 인정한다. HOF는 공식 일반 영입 28명 확률을 사용한다.
- 점수 1위 1명 + 응모권 추첨 1명에게 커피 기프티콘 각 1개. 마감 시 1위 참가자의 모든 응모권을 제외한다. 추첨 결과는 재추첨할 수 없다. 대상이 없으면 추첨 대상 없음으로 확정한다.
- 당첨자만 커뮤니티 쪽지로 실제 게임 속 덱과 참가 덱명을 운영자에게 보낸다. 참가 당시 등록 덱 사본과 대조하고, 운영자가 ‘게임 덱 인증 완료’를 기록한 뒤 실제 기프티콘 발송 후 ‘지급 완료’를 기록한다. 사이트는 인증 이미지·연락처를 수집하거나 기프티콘을 자동 발송하지 않는다. 인증 불가·미응답 시 자동 재추첨 규칙은 두지 않는다.
- 공개 예정 시각: 2026-11-09 00:00 Asia/Seoul. 종료 날짜는 미정이며 우선 운영자가 마감한다. SQL의 `ends_at`을 지정하면 종료 시각 이후 참여 요청도 서버에서 차단한다.

중복 방지는 **같은 등록 덱의 재참여**에 적용된다. 동일인이 다른 덱을 등록하는 것까지 자동 식별하지 않으며, 당첨 후 게임 덱 확인도 동일인 식별을 완전히 보장하지 않는다. 이 한계를 수용하고 참가 문턱과 개인정보 수집을 줄이는 운영 방식이다. 공개 화면에는 이메일·인증 ID·덱 소유 토큰을 노출하지 않는다. 운영자 이메일 로그인은 참가 인증과 별개다.

## 로컬에서 전 과정 확인

```sh
npm run dev:events
# http://localhost:5180/demo/event-pilot.html
```

가상 참가자 2명과 운영자를 선택할 수 있다. 참가자 선택 시 Auth에서 로그아웃하고 테스트 덱의 비밀번호 세션으로 참여하며, 운영자 선택 시에만 가상 Auth로 로그인한다. 실제 PostgreSQL SQL을 실행하는 PGlite DB를 `.event-pilot/`에 보관한다. 가상 Auth와 API는 127.0.0.1에서만 실행되며 실제 인증 메일을 보내지 않는다. 기본 포트는 웹 5180, API 8789이고 `EVENT_PILOT_WEB_PORT`, `EVENT_PILOT_PORT`, `EVENT_PILOT_DIR`로 바꿀 수 있다. 브라우저 새로고침과 서버 재시작 후 기록이 유지된다. 초기화는 서버를 끈 뒤 해당 테스트 DB 디렉터리를 별도로 보관하고 새로운 `EVENT_PILOT_DIR`로 시작한다.

```sh
node scripts/verify-events-db.cjs
# Playwright + /usr/bin/chromium이 설치된 환경:
node scripts/verify-events-browser.cjs
```

DB 검증: 이메일 계정 없이 덱 소유권 확인, 잘못된/누락된 세션 거부, 비밀번호로 다른 기기에서 복원, 동일 덱 중복, 5회 제한, 재요청 중복 차감 방지, 스킬 중복 제외, 서버 점수, 증거 없는 응모권 거부, 최대 4장, 먼저 달성한 동점자 우선, 마감, 중복 수령·재추첨 방지, 인증 전 지급 처리 거부, 운영자 전용 인증/지급 기록 및 재요청 중복 방지, 접근 권한, 마이그레이션 재실행 보존. 브라우저 검증은 별도 임시 DB를 만들며 운영 서버를 호출하지 않는다. 여러 요청은 PGlite의 한 연결에서 순차 트랜잭션으로 실행하며 실제 Supabase의 다중 연결 부하 시험은 별도다.

## Supabase에 적용

현재 작업 환경에는 Supabase DB 관리 자격 증명이 없어 원격 스키마를 직접 적용하지 않는다. 기존 덱 비밀번호 마이그레이션까지 적용된 프로젝트에서 아래를 수행한다. 운영 덱과 랭킹은 삭제하지 않는다.

1. SQL Editor에서 `scripts/supabase_mig_events.sql`, 그다음 `scripts/event-rules-v1.sql`을 실행한다. 두 파일을 한 파일로 만들려면 `node scripts/build-event-setup.cjs /원하는/경로/event-setup.sql`을 사용한다.
2. Authentication → URL Configuration의 Site URL을 `https://mlb-rivals-deck.pages.dev/`로 설정하고 Redirect URLs에 `https://mlb-rivals-deck.pages.dev/**`를 등록한다. 미리보기에서 운영자 로그인을 검증하려면 해당 **정확한 미리보기 호스트**도 등록한다.
3. **운영자 로그인용으로만** 이메일 로그인 공급자와 이메일 확인을 활성화한다. 기본 발송 서비스를 쓴다면 운영자 주소가 발송 허용 대상인지 확인하거나 SMTP를 설정한다. 참가자에게는 인증 메일을 발송하지 않으며, 참가 인원 규모에 따른 SMTP 설정은 필요하지 않다. 운영자 메일 수신과 사이트 복귀는 실제 서비스에서 확인한다.
4. 운영자가 이벤트 페이지 아래의 ‘운영자 로그인’을 펼쳐 이메일로 로그인한 뒤, Supabase SQL Editor에서 아래의 이메일을 운영자 본인 이메일로 바꿔 실행한다. 이메일을 소스에 커밋하지 않는다.

```sql
insert into public.sim_event_admins(user_id)
select id from auth.users
where lower(email)=lower('운영자_이메일') and email_confirmed_at is not null
on conflict do nothing;
```

5. `/?event=1#simulator`에서 운영자 관리가 나타나는지 확인한다. 새 이벤트는 **미공개 상태**이며 운영자가 ‘참여 접수 활성화’를 누르면 예약된 시작 시각부터 접수된다. 공개 전에 규칙·종료 시점·경품 안내를 확인한다. 시작 시각을 브라우저에서 바꿔도 참여할 수 없다.
6. 검증용 이벤트를 별도 Supabase에 만들거나 별도 이벤트 ID로 만들고 `VITE_EVENT_ID`를 지정해 원격 인증과 RPC 연결을 검증한다. 공개 이벤트에 테스트 참가 기록을 섞지 않는다. 확인 후 정식 배포 브랜치를 병합한다.

서버에는 `service_role` 키나 OpenAI 키가 필요하지 않다. 참가 RPC는 `p_ranking_id`와 비밀번호 인증 세션 `p_token`을 받아 서버에서 해시를 대조한다. 공개 조회는 세션 없이 가능하고, 개인 기록은 해당 덱 세션이 필요하다. 운영자 RPC만 Supabase 로그인 JWT와 `sim_event_admins` 권한을 요구한다. 기존 공개 랭킹·문의 읽기는 로그인 후에도 동작하도록 공개 컬럼에만 authenticated 읽기를 추가했다.

## 구현과 복구

- UI: `src/components/EventPage.tsx`, API 타입/오류 안내: `src/lib/events.ts`.
- 확률·점수표는 `coffee-sp-s-v1` 서버 규칙으로 고정한다. `generate-event-rules.ts`는 기존 공식 확률 데이터와 수정하지 않은 점수 엔진으로 SQL을 생성한다. 진행 중인 규칙은 교체하지 않으며 다음 대회는 새 버전을 만든다.
- 모든 변경은 이벤트 행 잠금 → 참가자 잠금 순서로 처리해 마감과 도전·발급의 순서를 보장한다. 도전 요청 UUID에 고유 제약이 있어 응답을 못 받은 요청도 재시도할 수 있다.
- 참가자, 시도, 발급, 체험, 운영 기록은 RLS와 테이블 권한으로 직접 접근을 차단한다. 공개 RPC는 필요한 필드만 반환한다. 조합의 섞인 순서는 카드 선택 전후 모두 비공개다.
- 공개·마감·추첨·당첨자 인증·지급을 운영자 ID와 서버 시각으로 기록한다. 인증/지급은 당첨자가 정해진 후에만 가능하고, 인증 전 지급 처리는 거부한다. 같은 처리를 재요청해도 기록은 한 번만 남는다. 마감 후 시도와 응모권을 추가하지 않으며 최종 추첨에는 대상 티켓 한 장을 암호학적 난수로 선택한다.
- 참가 당시 덱 사본은 참가 시 한 번 저장한다. 이후 랭킹 덱을 수정해도 사본은 바뀌지 않으며, 당첨자 사본은 운영자만 조회할 수 있다. 앞선 이메일 검증판 기록은 보존하면서 참가 Auth ID 열과 이전 RPC를 제거한다. 과거 사본 없는 기록은 운영 화면에서 별도 확인 안내를 표시한다.
- 순위와 전체 응모권을 현재는 한 번에 가져온다. 대규모 이벤트로 확장할 때 페이지네이션/집계 캐시를 추가한다.

## 외부에서 여는 HTTPS 체험 데모

Cloudflare의 `main` 이외 브랜치 미리보기 빌드에는 `/event-demo/`를 추가한다. `localhost:5180`은 개발 환경 내부 전용이므로 사용자에게 공유할 링크로 사용하지 않는다. 공유 시 해당 Cloudflare 미리보기 호스트의 `https://…/event-demo/` 주소를 사용하고 실제 배포본을 확인한다.

웹 데모는 실제 `EventPage`와 이벤트 SQL/확률표를 사용하되, PGlite를 브라우저에서 실행한다. 가상 참가자 A·B, 운영자, 비참가자 화면을 전환하고 데모 초기화로 다시 체험할 수 있다. 테스트 DB는 별도 IndexedDB에 저장되며 다른 탭에서 동시에 쓰지 않도록 잠근다. 실제 덱 저장소를 수정하지 않는다. 별도 빌드에서 Supabase URL/키를 빈 값으로 고정하고 운영자 이메일 로그인을 렌더링하지 않으며, 모든 요청은 브라우저 내부 DB에서 처리한다. 실제 서버 보안/동시접속 검증은 앞선 서버 테스트가 담당한다.

```sh
# 기존 dist/ 안에 체험 페이지를 추가한다.
node scripts/build-event-web-demo.mjs
# dist/를 제공하는 preview 서버에서 확인한다.
node scripts/verify-event-web-demo.cjs
# 외부 배포본도 같은 테스트를 실행할 수 있다 (실제 API 호출은 차단).
EVENT_DEMO_URL=https://미리보기호스트/event-demo/ node scripts/verify-event-web-demo.cjs
```

정식 `main` 빌드에는 데모와 WASM 파일이 포함되지 않는다. 실제 수집기 프로그램과도 무관하다.
